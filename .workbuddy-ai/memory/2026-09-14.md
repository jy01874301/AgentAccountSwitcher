## 诊断：Maggie ya 登录态只有 3 天（其余 60 天）

排查手法：解 `.info` 的 auth 字段 + 解 JWT payload（不解签名，只看 exp/iat/typ/scope/token_source）。

- 短期根因：该账号 refreshToken 的 payload 带 `token_source = "enterprise_switch"`，
  服务端对该通道下发 `expiresIn=259200`(3天) / `refreshExpiresIn=604799`(7天)；
  另外三个账号无 token_source（常规离线刷新），是 `5184000`(60天) / `7776000`(90天)。
  与切换器无关，是服务端签发策略差异。
- 附带发现（更严重）：`workbuddy-Maggie ya.info` 的 `auth.accessToken` 只有 4 字符 `"eyJx"`
  （base64 解出 `{"q`，明显被截断），文件内只存在 refreshToken 两段完整 JWT。
  → 这份素材是粘贴时被截断的，切过去客户端会拿到无效 accessToken。
- 漏洞：`workbuddy_checkin.refresh_account` 只校验 `accessToken.startswith("eyJ")`，
  "eyJx" 能通过；`wb_ui_server.add_account`/`switch_account` 也没校验 token 长度/段数。
  建议加校验：必须是 `eyJxxx.yyy.zzz` 三段且长度 > 200，否则拒绝写入/切换并提示。
- 桌面端另有一个 `workbuddy-desktop-ai.info`（nick=jnong24，exp=2027-09-11，1 年期），
  说明不同登录通道 TTL 差异很大（3天 / 60天 / 1年）。
- 修复 Maggie 的方式：客户端正常登录该账号后，整份复制
  `%LOCALAPPDATA%\CodeBuddyExtension\Data\Public\auth\workbuddy-desktop.info` 覆盖
  `wb_auth/workbuddy-Maggie ya.info`；若仍只有 3 天，则改用常规登录入口（非企业切换）重登。

## 定论：有效期由 JWT 的 token_source 决定（实测）

用户重新复制 desktop.info 并刷新后仍是 3 天。解开 accessToken payload 对照：

| token_source | access | refresh | 产生方式 |
|---|---|---|---|
| `oneid_login` | 5184000 (60天) | 7776000 (90天) | 常规 OneID 手机号登录 |
| `enterprise_switch` | 259200 (3天) | 604799 (7天) | 客户端切到企业空间的会话 |
| （无该字段，旧令牌） | 60天 | 90天 | 早期签发 |

- 同一时刻（09-14 14:21）连刷 4 个账号：只有 Maggie 是 259200，其余 5184000 → 排除客户端/脚本因素，
  确认是服务端按 token_source 的签发策略。续期沿用同一 token_source，所以短期续多少次都是短期。
- 好消息：**refresh 会滚动 RT**（每次续期后 RT 的 iat/exp 也重置为 7 天），只要每 ≤3 天续一次就不会掉线。
- `自动签到\config.json` 的 `wb_auth_dirs` 只含 `D:\AI项目\自动签到\wb_auth`，未含切换器的
  `D:\AI项目\wb_switcher\wb_auth`（两个目录各存 4 份相同账号，互为副本）。
- 结论补充：token_source **无法靠改本地文件/配置伪造** —— accessToken 是 RS256（服务端私钥签名），
  refreshToken 是 HS512（服务端对称密钥），改任何字符都会验签失败；`.info` 里的 expiresAt/expiresIn
  只是本地镜像，改了只会让前端显示错的天数，一请求就 401。
  翻遍 `%APPDATA%\WorkBuddy`（空）、`%LOCALAPPDATA%\WorkBuddy`（仅 logs）、
  `%LOCALAPPDATA%\CodeBuddyExtension\Data`（仅 auth）都没有 space/tenant 开关；
  客户端日志里只出现过 `https://copilot.tencent.com/v2/plugin/auth/token/refresh` 一个认证接口，
  没有可见的"切换空间"API。唯一可控变量是登录/刷新时的请求本身。
- **实验结论（已跑）**：改续期请求头无效。对 Maggie 连发 5 次 refresh
  （`X-Auth-Refresh-Source` = plugin/desktop/console/oneid_login/不带该头），
  全部 HTTP 200，`expiresIn` 恒为 259200、`token_source` 恒为 enterprise_switch、
  `sessionState` 始终是 `03e031d3-...`（同一会话）→ TTL 绑定在服务端会话上，请求头不是开关。
  实验方法：monkeypatch `wb.post_json` 注入/删除请求头 + 用临时副本 `workbuddy-__exp.info`
  承载轮换的 RT，最后一次有效结果回填正式素材（避免污染原文件）；原文件备份到 `.trash_20260914/`。
  → 唯一路径：让服务端重新走 oneid_login 通道签发（退出企业空间 → 退出登录 → 验证码重登）。
- 新增 `check_ttl.py`（只读体检）：列出每个 .info 的 token_source / 剩余天数 / accessToken 完整性，
  默认扫描 `wb_auth` 与 `../自动签到/wb_auth`。以后判断"为什么短期"先跑它。
